Every unit price is null, and that is correct. This GSA form is an unpriced solicitation — the price columns say "Do Not Quote" or "Government will provide dollar amount upon award." The model did not invent a single number, which is the behaviour that matters most for an ERP feed.

The four defects, precisely

1 · Three summary rows extracted as line items worst

CLINs 0001, 0002, and 0003 are group headers covering the sub-items beneath them. Their source text carries the tell:

0001  |  XXXXX Preventive Maintenance on Five (5) York / Carrier  0.00  |  Do Not Quote

An ERP fed this would create three phantom order lines. The fix belongs in the prompt: a row whose item number has no letter suffix and whose price says "Do Not Quote" is a grouping header, not a deliverable.

2 · Five prices claimed as supported with no amount caught

On items 12, 15, 19, 21 and 22 the model set unit_price.status = "supported" while leaving amount null — asserting it had found a price it had not. The validator caught all five, fired one automatic repair call, and the five survived it, so the run ended as completed_with_issues rather than success. This is the deterministic layer doing exactly its job.

3 · "Building 31" is not in the cited evidence attribution

Items 4 and 5 say Building 31. The string does appear in the document — twice, in the narrative sections. But the evidence ID they cite is the table row, which contains no building column at all:

ev_p2_t0_r0 = "3 | York 1200-ton 4160 volt | Yes | 2011"

So this is not a hallucination — the fact is real and in the document. It is an attribution failure: the value cannot be verified from the evidence offered. A reviewer clicking that citation would not find Building 31 there. Page 2's OCR dropped the building column that page 1 has, and the model filled the gap from context without citing where.

4 · One description is just the quantity minor

Item 0002AC has description "2.00 JB". The source cell genuinely contains only "2.00 JB" — the descriptive text landed in a different cell that the model did not pull in. A parsing/segmentation artifact, faithfully propagated.

GLM finds more; ox-alpha is more disciplined. GLM extracted all 21 real items but asserted prices it lacked and never declared abstention. ox-alpha found 18, declared /deadlines honestly, and linked each price row on page 4 to its ship-to continuation on page 6 — the multi-page table work paying off. GLM ignored pages 6 and 7 entirely.

Note what the status field did. Nemotron returned nothing at all and scored success, because an empty array is schema-valid. GLM returned the most usable data in the set and scored completed_with_issues. The status currently measures structural cleanliness, not whether the extraction is any good — a coverage rule is needed before that field means anything.

Verdict

The pipeline works and the data is largely correct. A reviewer handed this would accept 21 items, delete 3, fix 1 description, and re-check 2 citations. That is a usable first pass, and the review step the architecture requires is exactly where those corrections belong.
